# Stage D Protocol — Human Review of the Claim-Verification Evaluation Queue

**Dataset:** `d1` · **Schema:** v1.0.0 · **Generated:** 2026-10-16 · **Status:** prepared, awaiting human review
**Prepared by:** OpenCode (mechanical preparation: provenance audit, schema, guidelines, queue generation, validation). **No part of this document constitutes a human judgment.**

---

## 1. Purpose and boundaries

This protocol governs the first independent human annotation of the EvidenceGraph-AI evaluation claims, supporting the research question: *does claim-level evidence verification improve factual grounding and citation quality versus a standard RAG baseline for cybersecurity questions?*

Stage D boundaries (enforced by construction):

- No LLM/API calls were made in this stage; the queue is derived only from stored artifacts plus deterministic BM25 replay.
- No prompts, gate logic, application code, historical runs, or source corpus were changed. The protected source DB hash and both run DB hashes are pinned in `stage_d_manifest.json`.
- `gold_label` columns remain NULL everywhere. Nothing written here touches any database.
- The two pre-existing review files were read only; determinations about them are in `stage_d_provenance_audit.md` (the 56-claim file is an AI draft; the 8-claim mini file is `provenance_unknown` and excluded).
- This stage stops after this package. Stage E experiments and any commits require separate authorization.

## 3. Reviewer workflow (single or double pass)

1. **Read the guidelines** (§0–§4). Keep them open while reviewing.
2. **Close/ignore the full queue files during the first pass.** Work only in `human_review_queue_blind.csv`.
3. Work items in `annotation_id` order (= priority order: retracted → surviving supported → abstentions → stratified sample).
4. For each item: read the quoted evidence **first**, then the claim (or question), then write:
   - `human_label` (claim factuality) — or leave blank and explain in `uncertainty_notes`;
   - `evidence_sufficiency_rationale` (dimension B);
   - `citation_support_label` + rationale (dimension C); `not_applicable` when nothing is cited;
   - `abstention_assessment` for the 6 question items (dimension F);
   - `reviewer_id` **only if you choose to identify yourself**; `uncertainty_notes` for doubts, compound claims, injection sightings.
5. **Verdict visibility recording.** The blind file column `system_verdict_visibility` is preset to `blind_first_judgment_required`. If — and only if — you consulted verdicts (or the full queue) *before* finishing an item, overwrite that cell for those items with `visible_acknowledged` and say why in `uncertainty_notes`. This field is the audit trail for confirmation-bias exposure; honesty here is required, and self-reported exposure is recoverable while silent exposure is not.
6. **First-pass labels are the record.** After unblinding, do not silently edit a label. Post-hoc reflections belong in `uncertainty_notes`; a genuine reversal after seeing evidence you had missed should set `review_status = needs_adjudication` and explain the sequence. A label changed because the system's verdict persuaded you is contamination, not correction.
7. **Do not** add rows, rename `annotation_id`s, sort-destroying edits to key columns, or write anything to any `.db` file. Return the edited blind file (and full file, if you used it) as-is. Any queue change (extra items, schema change) is a new dataset version generated by `build_review_queue.py`, never a hand edit.
8. Timestamps: `review_timestamp` may be filled by the reviewer (UTC ISO-8601) or left null; it must never be pre-filled by tooling.

## 4. Pairing and interpretation notes

- Every claim comes from the **verified arm only** (the baseline performs no claim verification by design — there are no baseline claims to review). `paired_answer_texts` carries both arms' answers to the same question so you can compare systems at answer level on every item.
- The 6 abstention items are question-level: `claim_id`/`claim_text` are null, `system_verdict = abstained_no_claims`, and your judgment goes in `abstention_assessment`.
- **Recovered citations:** for the 13 retracted claims the post-gate store is empty *by design* (the gate rebuilds an abstention verdict). The queue restores the originally-cited ids from the gate anomaly note and asserts equality with the historical run's stored ids (13/13) at generation time; chunks are tagged `judge_cited_recovered_from_anomaly_note_and_historical_db` in the full queue (collapsed to `judge_cited` in the blind file to avoid leaking the retraction).
- **Reconstructed retrieval:** chunks tagged `question_retrieval_reconstruction_validated` come from deterministic BM25 replay, validated 22/22 against stored `retrieved_count` (Stage C method). Text is always verbatim from the run DB; only the *selection* is reconstructed, and it is marked as such.
- `system_diagnostics` (full queue only) shows the gate note and grounding ratio (bar 0.50, a judge configuration — not a human threshold). It is context for adjudicators, not evidence for labels.

## 5. Quality and adjudication plan (Phase E)

### 5.1 Second independent reviewer — contingent, not assumed

If a second human reviewer becomes available, both reviewers work **only** from the blind file, independently, without seeing each other's labels until both files are stored. No second reviewer has been identified; nothing in this package anticipates their identity.

**Double-review set (if a second reviewer exists):** all 30 decision-critical items — tier 1 (13 retracted), tier 2 (11 surviving supported), tier 3 (6 abstentions) — because gate precision, false-endorsement rate, and abstention quality all hang on them. Tier 4 (16 stratified unchanged) may be double-reviewed if capacity allows; otherwise it stays single-reviewed and is reported as such.

### 5.2 Disagreement identification

Join the two returned files on `annotation_id` and compare, per dimension separately:

- claims: `human_label`, then `citation_support_label`;
- abstention items: `abstention_assessment`.

Any mismatch → `review_status = needs_adjudication` for that item (both original labels preserved as-is). Dimension B rationales are compared qualitatively; a label match with contradictory rationales is also flagged.

### 5.3 Adjudication recording

- An adjudicator (a third party, or the two reviewers in a documented joint session — whoever actually exists) records `adjudicated_label` + `adjudication_rationale` and sets `review_status = adjudicated`.
- **Original `human_label` values are never overwritten**; adjudication lives only in the adjudicated fields. `adjudicated_label = unresolved` is the honest outcome when no agreement is reached.
- Adjudicator disagreement with both reviewers is allowed and must be explained in the rationale.

### 5.4 Agreement statistics (only after real labels exist)

- **Suitable for this sample size:** raw percent agreement per dimension with matched/total/coverage reported; **Cohen's kappa** for two raters on the double-labeled subset (n ≈ 30), reported *with* the raw agreement because with skewed prevalence (e.g. many `insufficient_evidence`) kappa is unstable at this n. Per-label confusion table always reported.
- Krippendorff's alpha only if >2 raters or substantial missingness arise. No significance tests on clustered small-n data (Stage C lesson stands).
- **No agreement statistic is computed before human labels exist.** Nothing in Stage D computes one.

### 5.5 Missing labels and uncertain cases

Blank labels are excluded from agreement denominators and reported as coverage (`matched / total / coverage` per dimension). `uncertain` (abstention dimension) counts as a legitimate review outcome, not missing data, and is reported separately. Never convert blanks or `uncertain` into a label by tooling.

### 5.6 Why AI labels cannot substitute for human annotation

The AI-draft labels come from the same model family under evaluation; treating them as ground truth would measure the system against itself (circularity), not against independent judgment. The provenance audit shows the draft disagrees with the judge on 33/56 claims — that disagreement is *AI vs AI*, not signal. AI labels remain quarantined in `proposed_ai_label` (absent from the blind file, barred from agreement statistics).

### 5.7 Single-reviewer limitation (state honestly)

With one reviewer, the resulting dataset is **human-reviewed by a single annotator — not independently validated**. There is no inter-rater agreement to report, adjudication fields stay empty, and downstream text must say "single-reviewer human labels (n=…, coverage=…)" rather than "human-verified" or "independently validated." This limitation is a property of the data, not a wording preference.

## 6. After the review (gated on separate approval)

1. Transfer step to any `gold_label` field requires the reviewer's explicit approval and a separate authorization — it is not part of returning the files.
2. Compute agreement/coverage reports (single-reviewer mode per §5.7) as a new artifact; historical runs stay untouched.
3. Stage E experiments (generate-once, ≥3 repeats, gate ablation, baseline-claim extraction) and Stage F statistics/manuscript follow only with approval.

## 7. Stop condition

This stage ends with: provenance audit, schema, dictionary, guidelines, queue (46 items), protocol, manifest, and validation report delivered for human review. No annotations are filled in by tooling; no stage begins without the owner's go-ahead.
